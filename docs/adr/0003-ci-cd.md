# ADR-0003: CI/CD with GitHub Actions and rsync over SSH

**Status:** Accepted (owner, 2026-11-22)
**Date:** 2026-11-22
**Deciders:** Owner

## Context
- Hostinger's Git deploy only pulls files into `public_html`. It does not run `composer` or `npm`, and it does not fit ADR-0002's release layout.
- The server has no Node, and heavy work (npm, large composer installs) on the shared server is forbidden by CLAUDE.md.
- The server has `rsync`. SSH key auth works (custom port).
- Branches: `development` deploys to `dev.chinmoybiswas.com` and `main` deploys to `chinmoybiswas.com`.

## Decision
**GitHub Actions** with three workflows:

1. **`ci.yml`**: runs on every PR and every push to `development`/`main`.
   - PHP 8.3 (same extensions as the server), `composer install`, `pint --test`, `phpstan` (Larastan), `pest --parallel` against a **MariaDB 11** service.
   - Node LTS: `npm ci && npm run build`. A failing build blocks the merge.
   - Playwright smoke tests run against `php artisan serve` with the seeded DB (TESTING.md).
2. **`deploy.yml`**: runs on push to `development` (environment `staging`) or `main` (environment `production`, with **required reviewer = owner**). It only runs after `ci` succeeds (`workflow_run` or `needs`).
   - **Build:** `composer install --no-dev --optimize-autoloader --classmap-authoritative`, `npm ci && npm run build`. Then remove `node_modules`, `tests` and `.git*`, and write `public/build`. Record the version in `RELEASE` (`<UTC timestamp>-<short sha>`).
   - **Upload:** `rsync -az --delete` to `~/domains/<d>/app/releases/<id>/`, using `--link-dest` pointing at the previous release to save bandwidth and inodes.
   - **Activate (one SSH session running the `deploy/activate.sh` that was uploaded with the release):**
     1. Link `.env`, `storage` and `public/storage` to `shared/` (ADR-0002).
     2. `php artisan migrate --force --isolated`
     3. `php artisan optimize` (config, routes, views, events) + `php artisan filament:optimize`
     4. Switch `current` atomically, call the opcache-reset endpoint, and run `php artisan queue:restart` (a no-op apart from the cache flag).
     5. **Health check:** `curl -fsS https://<d>/up` (Laravel health route) must return 200 and show the new `RELEASE`. If it fails, switch `current` back automatically.
     6. Prune releases so the last 3 remain.
   - `concurrency: deploy-<env>` so two deploys never overlap.
3. **`rollback.yml`**: manual `workflow_dispatch` (choose env + release id). It switches `current` and resets opcache.

**Secrets** (GitHub Environments, separate for staging and production): `SSH_HOST`, `SSH_PORT`, `SSH_USER`, `SSH_PRIVATE_KEY` (a dedicated ed25519 deploy key, no passphrase, used **only** by CI), `SSH_KNOWN_HOSTS` (pinned host key), `DEPLOY_PATH`, `APP_URL`, `DEPLOY_TOKEN` (for the opcache endpoint). The app `.env` **stays on the server only**.

**Migrations:** use expand/contract only (add columns and tables, backfill, and remove them in a later release). This keeps rollback safe because migrations run *before* the switch. Destructive migrations need an explicit note in the PR and a `mysqldump` step before them (the workflow input `backup_db: true` runs `mysqldump` into `~/backups/`).

## Options considered

### A: GitHub Actions + rsync over SSH (chosen)
| Dimension | Assessment |
|---|---|
| Complexity | Medium: one workflow and one shell script |
| Cost | Free (public repo, unlimited Actions minutes) |
| Server load | Minimal: rsync of changed files plus artisan commands |
| Rollback | Instant (ADR-0002) |

**Cons:** the deploy key gets a shell on an account that also hosts two other sites (see Risks).

### B: Hostinger Git webhook deploy from a built `deploy-*` branch (fallback)
CI commits the built artifact (including `vendor/` and `public/build`) to an orphan branch, and Hostinger's Git integration pulls it.
**Pros:** CI never needs an SSH key. **Cons:** it pulls into one fixed directory, so there are no release folders and no instant rollback. It cannot run migrations or caches, so a cron or web hook is needed for those. It puts vendor code in git history. Use only if SSH from GitHub runners gets blocked.

### C: Build on the server (`git pull && composer install && npm build`)
Rejected: there is no Node on the server, and CLAUDE.md forbids heavy work there.

### D: Pull-based deploy, with no SSH key in GitHub (considered; the owner chose A on 2026-11-22, and D stays as the switch-over option if the key risk becomes unacceptable)
CI builds the release, attaches `release-<id>.tar.gz` + `sha256` to a GitHub Release (the repo is public, so the download needs no token), and updates a tiny `deploy/<env>.json` pointer. A cron job on the server (every minute) runs `deploy/pull.sh`. That script compares the pointer with `current`, downloads and verifies the tarball over HTTPS, unpacks it into `releases/`, and runs the same `activate.sh` steps.
**Pros:** **no credential that can log in to the shared account ever leaves the server**, which removes the blast-radius risk below. **Cons:** about 1 minute of latency, CI can only confirm success by polling `/up`, and there is one more script to maintain. The server needs `curl` and `tar` (present).

## Risks and mitigations
- **Deploy-key blast radius (Option A only):** all websites on the account run as **one Unix user**, so this key can read and modify every site's files and their DB credentials, not just ours. Mitigations: dedicated key, used only from GitHub Environments; **the build job (composer/npm scripts, i.e. third-party code) never has the key**, because only a separate deploy job, which downloads the built artifact and runs no package scripts, gets the secret; actions pinned to commit SHAs; production needs manual approval; `activate.sh` only touches `$DEPLOY_PATH`; rotate the key every 6 months and after any leak suspicion. If Hostinger honours `authorized_keys` options, restrict it with `restrict` plus `from=`. GitHub runner IPs vary, so this is optional.
- **Host-key spoofing:** `StrictHostKeyChecking=yes` with the pinned `SSH_KNOWN_HOSTS`.
- **Partial upload:** a new release dir is never live until `current` is switched.

## Consequences
- Easier: reproducible builds, green CI before every deploy, and one-click rollback.
- Harder: someone must create and maintain the deploy key and secrets (see the Phase 3 manual steps).
